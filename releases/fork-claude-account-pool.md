# Paperclip fork: Claude account pool

> Fork release on top of v2026.1012.0. It replaces the fork's host account pools; the previous image is fork commit `d6f6d1cad`.
>
> Since the [upstream sync of 2026-10-21](fork-upstream-sync-2026-10-21.md) the fork migrations this note names `0309` and `0310` are `0374_smooth_killmonger` and `0375_productive_veda`, and the fork's `0306`–`0308` are `0371`–`0373`. Production applied them under the old numbers; their content is unchanged.

This fork release replaces the host account pools with a Claude account pool that users own. Each user adds their own Claude accounts once and uses them in every company where they are an active member; the owner or a company admin binds an account to each Claude agent, and the agent's runs use it on whatever device they run on. One product rule holds everywhere: Paperclip never moves a task to another account. When an account hits its limit, its tasks wait for the reset, start again on the same account, and the task's manager agent and the board get a notice at once. Around that: hosts become execution devices with at most 3 accounts each, an unavailable device or account makes a task wait with a clear banner instead of failing it, a one-time boot job binds the agents that used a host pool, and environment driver plugins get an API to report their targets. Underneath, remote targets no longer receive the server's environment, SSH runs keep secret values off the command line, and only the Claude CLI's own output can mark an account limited or signed out. The full contract is in [AI Connections](../doc/connections/AI-CONNECTIONS.md#claude-account-pool-fork); the design is in [the plan](../doc/plans/2026-10-16-claude-account-pool.md).

## Breaking Changes

- **No automatic account choice and no failover.** Host-pool selection, balancing and the `ai_connection_failover` hand-off are gone. A limit or a sign-in failure makes the task wait for the same account. An agent without a binding never receives a pool token: it uses its own AI connection, or the device's own login.
- **Claude agents need a binding to use a pool account.** The boot job binds the agents that used a host pool or a company pool, and marks those bindings for review. Agents it cannot bind safely wait as `unassigned` with a notice instead of falling back to the device's login, or stay as they are and appear in the migration report.
- **The company account pool is retired, and routers are refused for Claude agents.** A new or changed `company_pool` binding is refused for every adapter (422 `ai_connection_company_pool_retired`), and a `router` binding is refused for a `claude_local` agent (422 `ai_connection_router_unsupported`). An existing agent that keeps its current binding keeps running: a company-pool agent stays on the member it used last and waits for that member's reset, and the pool no longer reads usage to skip a member. A pinned member that fails a check fails the run instead of being skipped. Marks that the usage probe of an older release left (quota source `usage_probe`) are no limit: they never hold a run or extend a later limit, and the pool card, now titled "Company account pool (retired)", shows neither usage readings nor a limit badge for them.
- **A proxy in a pool run's environment is refused.** A pool run whose environment, agent, project or routine layer sets `HTTP_PROXY`, `HTTPS_PROXY` or `ALL_PROXY` (any case), `NODE_EXTRA_CA_CERTS`, `NODE_TLS_REJECT_UNAUTHORIZED`, a `*_BASE_URL` key under `ANTHROPIC_` or `CLAUDE_CODE_`, or any `CLAUDE_CODE_USE_*` switch fails with `ai_connection_incompatible`; so does a project `.claude/settings*.json` that sets such a key, a credential carrier, `apiKeyHelper`, `awsAuthRefresh` or `awsCredentialExport`. SSH pool runs also unset these keys after the login profiles. A network that needs a proxy cannot run pool agents yet.
- **Legacy host-pool account routes return 410.** `POST /api/instance/ai-hosts/:hostId/accounts` and `PUT /api/instance/ai-accounts/:id/projects` answer 410 to every caller, with code `ai_account_route_moved` and the routes that replace them in `details.replacements`. `PATCH`, `POST …/clear-limit` and `DELETE /api/instance/ai-accounts/:id` are now the account pool's instance routes: `PATCH` takes only `{adminDisabled, reason, ownerUserId}` (the old fields are refused), and `DELETE` answers 409 `ai_account_in_use` while agents use the account, unless `?release=true`. Host listing, host create, update and delete, and environment mappings stay; a mapping edit that gives a device an account over its cap, or lowering a cap below its bound accounts, returns 409 `device_account_limit`. Device changes are logged only in the companies whose agents use the device, no longer in every company.
- **Unavailable devices make tasks wait.** An unreachable SSH host or a plugin target that reports itself unavailable no longer fails the run as `setup_failed`: the run ends as an expected cancellation and a waiting run resumes the task. `PAPERCLIP_ENVIRONMENT_WAITS=off` restores the old behaviour (see the Upgrade Guide).

## Highlights

- **Your own Claude accounts** — Company settings → Claude accounts lists "My Claude accounts" for every member. Paste a `claude setup-token` subscription token or an API key, or import your own saved Claude connection; instance admins can also import the server's environment token into their own pool. Tokens never come back from the API. Owners pause, resume, rename, replace the token, clear a limit or remove an account; a signed-out account offers Replace token and Remove instead of Pause. Each account is usable only in companies where its owner is an active member.
- **Agent assignments** — The same page lists every Claude agent with a picker. A Claude agent's Configuration view has a Claude account field in its Adapter section, in place of the AI connection field: it says what the agent's runs use now, and what to do when they cannot run, and offers the agent's AI connection only while that is what the agent uses. The overview names the same choice, and its Change link opens the field. The owner of an account or a company admin binds it; agents never do. A change applies from the next run and never interrupts a running one. Migrated bindings show a "Review migrated assignments" banner with Confirm all.
- **Execution devices** — Hosts become devices: the Paperclip server (Local), each SSH host (`ssh:<host>:<port>`), and the targets an environment driver plugin reports. A device uses at most 3 distinct pool accounts, checked when an account is bound or an agent moves and again when a run starts. Company settings → Devices shows availability, accounts in use, waits and a display-only owner; Instance settings → Devices & Claude accounts adds caps, environment mappings, links for one machine reached two ways, admin disable, owner transfer and the migration report.
- **Waiting instead of failing** — A task whose device, account or device slot is unavailable shows a banner such as "Waiting for device \<name> (offline since 13:02)", stays in progress with its agent idle, and starts automatically. The run ledger folds the waits into one "Waited: \<reason>" entry. Check now forces a check and answers "Still unavailable (checked just now)" while the resource is down. Comments on a waiting task no longer move it back to todo.
- **Limits wait for the reset** — A usage limit waits until the provider's reset (clamped to 7 days and 1 hour), or an estimate of 1 hour that doubles up to 12 hours; an exhausted API credit balance waits 24 hours. At the reset one waiting task goes first as a probe, and the rest follow when it is served. The task gets an immediate notice: "Paperclip never moves a task to another account. The owner can clear the limit after checking."
- **Notices that name the fix** — Problems a person must fix (a signed-out token, an account that was paused or whose owner left the company, a device that does not take the project, a credential type a device refuses, a full device) notify the task, the inbox and the manager agent at once. Long device waits notify after 24 hours by default. Blocked tasks get specific notices: "Execution device refused the run", "AI account blocked by a conflicting setting" and "AI account of a suspended run changed".
- **Plugin targets API** — Environment driver plugins can throw a typed `paperclip/environment-unavailable/v1` envelope, opt into receiving `projectId`, answer an optional `environmentCheckAvailability`, report their targets with `ctx.environments.reportTargets`, and create a company's environment from a board user's action with `ctx.environments.ensureCompanyEnvironment`. Only rebuilt plugins use it; it adds no capability or manifest field.
- **API** — The OpenAPI document covers every account pool, device, wait and legacy host route, with coded errors (codes and `details`). The instance routes are marked instance-admin, and the two retired routes are documented as a 410 for every caller. On upstream routes (agent create, hire, `PATCH`, config rollback, approval approve) the fork's error codes are listed in `x-paperclip-error-codes` and their details in `x-paperclip-error-details`; `code` and `details` stay open there. The fork's own routes keep a closed code enum. Account pool requests are secret-sensitive in the HTTP log: a failed `POST`, `PUT` or `PATCH` to `/api/me/ai-accounts*` or `/api/instance/ai-accounts*`, or to the retired `POST /api/instance/ai-hosts/:hostId/accounts`, is logged without its error text, and a server error there answers only `Internal server error`.

## Fixes

- **Remote targets get the run's environment only** — Install steps, resolvability probes and similar commands of claude-local and the other audited local adapters no longer merge the server's own process environment (`DATABASE_URL`, `BETTER_AUTH_SECRET`, the server's `PAPERCLIP_*` keys) into what they send to sandbox and SSH targets.
- **No secret values on the ssh command line** — Every env value except those under a short list of known non-secret names (such as `PATH`, `HOME`, the locale and Paperclip's run ids) is written over stdin into a private file on the host, sourced after the login profiles and deleted before the command starts. A secret is therefore kept off the command line whatever name it is bound to, `DATABASE_URL` or `GH_PAT` included. This costs one extra ssh connection per command that carries such a value; agent runs already carry one. Bridge start and other SSH commands stage values the same way.
- **Only the CLI's own output marks an account** — Claude limits and sign-in failures are read from the CLI's result and error output only, never from tool output or the transcript; a limit wins over a sign-in marker. A first untyped sign-in failure waits 10 minutes for that run only; a typed 401 or 403, or a second failure on another run within 2 hours, marks the account signed out.
- **A per-account Claude config directory on sandbox and SSH targets** — Pool runs there use `config-<ref>` for their account, seeded from settings without `env`, `apiKeyHelper` or the AWS helpers and without stored credentials, so a device user's own login can never back a pool run. Local pool runs keep the current config directory.

## Upgrade Guide

Upgrade in this order. Steps 1 and 2 run while production still runs the current image.

1. **Pre-deploy report (read-only).** Run it against production and keep its output with the release:

   ```sh
   psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -f scripts/ai-account-pool-report.sql > ai-account-pool-report.txt
   ```

   It writes nothing and works on the current schema. It lists the accounts with their creators (the owners `0310` sets) and reservations, the hosts with the device keys `0310` derives and the hosts it cannot key, the agents with host-pool runs in the last 45 days and the accounts they used, the company-pool agents, account owners who are not members where their accounts ran, the sandbox environments and, in section 10, the agents the go/no-go covers.

2. **Snapshot rehearsal and go/no-go.** Copy production into a throwaway Postgres (at least production's major version: run `SHOW server_version;` on production) with a read-only `pg_dump`, under a database name that contains `rehearsal` or `snapshot`; the 45-day history and the 7-day go/no-go window count back from the time of the run. Do not restore one of Paperclip's built-in backups for this: their format keeps primary, unique and foreign keys but no CHECK constraints, and `0309` drops the check on `ai_account_hosts.kind`, so the rehearsal stops at `0309` on such a copy while production has the constraint. A `pg_dump` copy, or a fork of the managed database, keeps them. Then run the new image's rehearsal script against it. With Docker, for example, on a host that has the new image and can reach the production database:

   ```sh
   docker network create <rehearsal-net>
   docker run -d --name <rehearsal-db> --network <rehearsal-net> \
     -e POSTGRES_USER=<user> -e POSTGRES_PASSWORD=<password> -e POSTGRES_DB=paperclip_rehearsal \
     postgres:<major version>
   docker exec <rehearsal-db> pg_isready -h 127.0.0.1 -U <user> -d paperclip_rehearsal   # repeat until it accepts connections
   docker run --rm --network <rehearsal-net> --env-file <file with production's DATABASE_URL> -e PGPASSWORD=<password> postgres:<major version> sh -c \
     'pg_dump "$DATABASE_URL" --no-owner --no-privileges --lock-wait-timeout=5s | psql -h <rehearsal-db> -U <user> -d paperclip_rehearsal -v ON_ERROR_STOP=1 -q'
   docker run --rm --network <rehearsal-net> \
     -e PAPERCLIP_REHEARSAL_DATABASE_URL='postgres://<user>:<password>@<rehearsal-db>:5432/paperclip_rehearsal' \
     -e PAPERCLIP_DEPLOYMENT_MODE=<production's deployment mode> \
     <new-image> node --import ./server/node_modules/tsx/dist/loader.mjs \
     server/dist/scripts/ai-account-pool-rehearsal.js --snapshot > ai-account-pool-rehearsal.json
   echo "exit code $?"   # 0 go, 2 no-go, 1 error or refusal
   docker rm -f -v <rehearsal-db> && docker network rm <rehearsal-net>   # -v also removes the copy's data volume
   ```

   The rehearsal command replaces the image's server command, so no server starts; pass it no production environment file (only the `pg_dump` step reads production's `DATABASE_URL`, and only reads). Pass production's deployment mode, which the summary prints as `Deployment mode`: without a config file the script falls back to `local_trusted`, where the local board user counts as a member of every company. The script needs only `PAPERCLIP_REHEARSAL_DATABASE_URL`, never reads `DATABASE_URL`, refuses a database whose name lacks `rehearsal` or `snapshot`, and starts no scheduler, heartbeat, plugin worker or HTTP server. It applies the migrations, runs the binding backfill and writes the migration report with its go/no-go to stdout as one JSON document. The terminal shows a summary: the outcome counts, the devices at or over their cap, the agents left unassigned or unbound with their notes, the agents that block go, and, as a warning, the agents at their account's limit, which wait for its reset on the same account. Go (exit 0) means every `claude_local` agent with a host-pool run in the last 7 days plans to `use` its account, or only waits for that account's limit to reset (`wait` with `usage_limit` or `credit_balance`: the account resolved and passed every other check, so these are listed as warnings); any other plan (another `wait`, `none` for the device's own login, or `refuse`) blocks go (exit 2). Exit 1 is an error or a refusal, with the reason on the terminal; a failed backfill exits 1 even when the go/no-go would pass.

   Fixes made on the copy do not carry over, and bindings exist only on the new image. So on production, still on the current image, fix what it can fix: put the account back in the pool or set it active again, clear its project reservation, add its owner to the company, or pin the agent or move it to a device with a free slot. Pause each agent that still needs a deliberate binding: you bind it right after boot (paused agents can be bound) and then resume it. Then rehearse again on a fresh backup. The go/no-go counts paused agents too, so the rehearsal stays no-go for the agents you paused; deploy once every agent that still blocks go is one of them, or one whose unassigned note says Paperclip cannot tell which device a plugin's sandbox environment runs on. Such an entry is expected until that plugin is upgraded and reports its device (step 6): the backfill runs at boot, before any plugin worker starts. Do not pause or pin those agents for it; step 6 gives them their account. Booting a copy of the new image with the scheduler off, on an isolated host, is an optional extra check (see [Binding backfill](../doc/connections/AI-CONNECTIONS.md#binding-backfill)).

3. **Core deploy, while no runs are active.** Deploy in a quiet window: wait until no run is running (for example, `SELECT count(*) FROM heartbeat_runs WHERE status = 'running'` returns 0), take a database backup, then deploy the new image. A `host_pool` run still running at the deploy would count toward its device's limit until it finishes. Migrations `0309`–`0310` run at startup. `0309` is DDL only: owner, origin, admin-disable, limit-strike, probe and sign-in-suspicion columns on `ai_accounts`, whose `host_id` becomes nullable with `ON DELETE SET NULL` and whose e-mail uniqueness becomes per owner; device keys, plugin target fields, a display owner and an over-limit flag on `ai_account_hosts`, plus the kind `external`; and the new tables `ai_account_agent_bindings`, `ai_account_run_slots`, `environment_availability`, `resource_wait_episodes`, `resource_wait_notices`, `execution_wait_settings` and `deferred_data_migrations`. `0310` is data only: each account's owner becomes its creator, existing accounts are marked `legacy_host_pool`, accounts that were "Not in pool" become "Paused by owner", and existing hosts get their device keys where their environments agree on one host and port. `0310` inserts no bindings.

4. **Boot backfill and its report.** The binding backfill runs once at boot, after the migrations and before the scheduler starts (marker `ai-account-bindings-v1`). A failure is logged, recorded on the marker and retried at the next boot; it never blocks boot. Read its report right after boot: `GET /api/instance/ai-accounts/migration`, or Instance settings → Devices & Claude accounts → Assignments from the host pool. It should match the rehearsal; a `failed` status carries the error in `lastError`. Instance admins re-run the backfill there with Run again, or with `POST /api/instance/ai-accounts/migration/run`. A re-run adds missing bindings, and gives an account to the rows it left unassigned that nobody has changed or reviewed since, once their checks pass; any other row stays as it is.

5. **Reviews, right after the deploy.** Bind the agents you paused before the deploy, then resume them. Company admins review the migrated bindings (the banner on Claude accounts, or `POST /api/agents/:agentId/ai-account/review`) and the agents the report lists with a review note. An unpinned agent is checked against every candidate environment, its company's project defaults included, so one whose company has a project on a plugin's sandbox environment waits `unassigned` until that plugin reports the environment's device; its note says Paperclip cannot tell which device the environment runs on. After the plugin's first report (step 6), re-run the backfill (Run again) and read the go/no-go. Do not pin such an agent: a pin wins over the project default and moves the project's work to the pinned environment. Until the plugin reports, an instance admin can instead map the environment to a device and then bind the agent by hand. If an admin added an account on someone else's behalf, an instance admin transfers it with `PATCH /api/instance/ai-accounts/:id {ownerUserId}`; an account without a recorded creator stays unusable until it is transferred or deleted. Then read the go/no-go again on production: it must be go.

6. **Environment driver plugins that report targets** upgrade after the core. A plugin that is not rebuilt keeps working as before: it gets no `projectId` and no reports reach the core, so its environments have no device (pool bindings to them get 422 `device_unknown`) and an unavailable target still fails runs as `setup_failed`. Then rebuild the plugin against the new SDK, which it bundles, and opt into `projectId` only once it handles runs without a project. A plugin installed from a local path that requests a capability the installed version does not have cannot use `POST /api/plugins/:pluginId/upgrade`: the route stops the plugin first, then the loader refuses the new capability ("introduces new capabilities that require approval") with a 400, and the plugin is left `ready` without a worker. `POST /api/plugins/:pluginId/enable` refuses a `ready` plugin, and no route approves a capability. Instead, copy the new files into the plugin's directory, wait until no run on its environments is running, then call `POST /api/plugins/:pluginId/disable` and `POST /api/plugins/:pluginId/enable` back to back. The activation re-reads the manifest from the plugin's directory, stores it, applies new migration files and starts the worker with the capabilities it declares, so the instance admin who enables the plugin approves them. The `enable` response is the plugin record from before the activation and still shows the old version: read `GET /api/plugins/:pluginId` afterwards for its `status`, `version`, `lastError` and `manifestJson.capabilities`. While the worker restarts, runs wait as `restarting` and start once it is up, at the latest at their 30-second re-check; a lease that starts while the plugin is `disabled` fails as `configuration_incomplete`. If the activation fails, the plugin is left in `error` with the reason in `lastError`; `enable` alone retries it, also after the previous version's files are put back (`upgrade` and `disable` answer 400 for a plugin in `error`). As a fallback, uninstall without purge (`DELETE /api/plugins/:pluginId`) and install again from the same path (`POST /api/plugins/install {"packageName": "<path>", "isLocalPath": true}`): this reuses the plugin's row, id, settings and data, and a migration that fails inside the install leaves the plugin `uninstalled`, so only another install brings it back. A version that only drops capabilities can use `POST /api/plugins/:pluginId/upgrade`. After the first report, link each target that is the same machine as an existing SSH device (Instance settings → Devices & Claude accounts, or `POST /api/instance/devices/:id/link-target`) before binding pool accounts to its environments. Then re-run the binding backfill (Run again, or `POST /api/instance/ai-accounts/migration/run`) so the agents boot left unassigned for want of that device get their account, and read the go/no-go again. On a previous core, a rebuilt plugin gets `METHOD_NOT_FOUND` from both host methods; it should stop calling them and create environments through the admin REST API.

Settings and later releases:

- **The kill switch** `PAPERCLIP_ENVIRONMENT_WAITS=off` (also `false`, `0` or `disabled`) turns device waits off. It is read once at startup, so it takes effect only after a server restart (a container restart in Docker). With it off, environment errors fail runs as before this release, and each run already waiting for a device gets one real attempt. Account and slot waits cannot be switched off.
- **The notify-hours setting** sets when a long device wait notifies: Company settings → Devices → Waiting notifications (company admins), or `PUT /api/companies/:companyId/execution-wait-settings {notifyAfterHours}` with 0 for never and at most 168. `null` ("Instance default" in the UI) uses the instance default, `PAPERCLIP_RESOURCE_WAIT_NOTIFY_HOURS` (24 when unset, 0 for never, at most 168). The same card turns the manager agent's wake on or off for limits and problems a person must fix (on by default) and for long device waits (off by default). Limits and problems a person must fix always notify the task at once.
- **Later releases** remove the legacy `host_pool` slot counting, the `ai_connection_failover` handling and the 410 routes, after one stable release.

## Emergency rollback

Redeploying the previous image (`d6f6d1cad`) is for emergencies only. The product rule does not hold while it runs: it resumes balanced host-pool selection and failover for mapped hosts.

- The schema stays: migrations `0309` and `0310` are not reverted, and no data is lost.
- The old image ignores bindings, owners, wait episodes and the availability registry.
- It selects accounts by host, so accounts without a host, which is every account added after the upgrade, are invisible to it.
- Deleting a host no longer deletes its accounts, because their foreign key is now `ON DELETE SET NULL`.
- A duplicate e-mail hint from the same creator returns 500 instead of 409, because the old image only knows the old index name.
- Plugin devices show the raw kind `external`. A rebuilt environment driver plugin gets `METHOD_NOT_FOUND` from both host methods and receives no `projectId`; it should stop reporting and create environments through the admin REST API.
- Paused and admin-disabled accounts stay out of the old host pool, because `pool_enabled` is kept in step with them.

When you return to the new image, re-run the binding backfill from the migration report to bind agents that have no binding yet (for example agents created meanwhile); agents that already have one keep it, except that a row the backfill left unassigned and nobody has changed or reviewed gets its account once its checks pass. An account switched out of the pool on the previous image is active again here: its owner pauses it, or an instance admin disables it. Then run the go/no-go again.

## Known residuals

- Local runs can read the server's master key and could decrypt every pool credential. This is pre-existing; Local pool runs also keep the server user's stored login and settings. Hardening Local execution is a separate project.
- Runs under one OS user on one device can read each other's environment, including a concurrent pool run's token.
- A remote device user whose own `~/.claude/settings.json` sets `apiKeyHelper` or an auth key blocks pool runs on that device through upstream's project-auth check.

See [Known residuals](../doc/connections/AI-CONNECTIONS.md#known-residuals) for the full list.
