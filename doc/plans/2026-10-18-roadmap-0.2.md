# Roadmap 0.2-0.4: plan-bound versions, a standing fix stream and Inbox-driven releases

- Date: 2026-10-18 (design); board decisions 2026-10-19.
- Status: **approved by the board on 2026-10-19, not implemented yet.** The board accepted every recommendation (§14), and §17 gives the execution order. The design was revised after three verification passes: liveness and invariants, platform feasibility, and user flow and DevOps. Every load-bearing behaviour was checked in code, and §16 lists the facts with path:line.
- Owner: board operator.
- Applies to: fork branch `deploy/2026.1012.0` at `45eb67709`, and every company on the instance. The code changes are the `paperclip.roadmap` plugin (`packages/plugins/roadmap`, v0.1.0 today) and three small core seams that ship together in one overlay (§8).
- Relationship to rev5: an additive, dated delta on `doc/plans/2026-10-06-epics-and-versioned-releases.md`, which stays as written (AGENTS.md rules 4-5). §15 lists what carries over, what is deferred and what diverges.
- Words: the board's "roadmap" is one **feature version** of one project, with its own tasks (§2.3). Example companies are neutral: Acme, Initech, Globex.

---

## 1. Summary

Each roadmap becomes a stored version row in the existing `paperclip.roadmap` plugin. The plugin takes every deterministic step itself, so agent runs go only to work that needs judgement.

Each version gets one **anchor** task, for example `Roadmap: Acme iOS 1.3`. The plugin creates it in the name of the project's Roadmap owner, a board member, and leaves it **unassigned** except while the PM is taking a turn on it. The anchor has three jobs:

- it is the planning thread with the PM;
- it is the parent of every task the plugin creates for the version;
- it holds every notice and decision card, which therefore arrive **unread** in the owner's Inbox.

**Agents never call the plugin.** They write one named JSON document on a task they already hold: `version-plan`, `roadmap-fixes` or `release-record`. They use core routes that server-hosted agents, native runners and remote device sandboxes can all reach.

**An approved plan becomes parked tasks.** "Parked" means unassigned and in `backlog`, the one state that no wake path touches. Nothing runs until the board presses **Start**. A throttled engine then hands the work to the planned owners. It moves at most 3 tasks to assigned `todo` per company per rolling minute, and it counts these moves from persisted rows.

**Finishing and releasing.**

1. When every task of the version is closed, the board gets an unread notice and a **Cut now?** card.
2. Each project keeps one standing **fix stream** that collects daily fixes until the board cuts a patch. A feature cut also carries the stream's finished fixes, because they are already on `main`.
3. Every cut drafts release notes. It also gives DevOps a generated release task that carries the tag, the git mode and a record format.
4. Before marking the version released, the plugin checks two things: the release record, and the board's go/no-go (or a Confirm click when the project has no publish gate). Then it offers **Start 1.4?**

**Core seams.** Three small seams ship once, in one overlay, before the plugin creates any work task:

- **S8:** normal run recovery for plugin work tasks;
- **S5:** a normalized execution policy on plugin writes;
- **S12:** plugin document updates with a base revision.

**Cost.** Covering U1-U9 takes about **19-21 engineer-days** (rev5 estimated 28-33). First value on Acme comes after about 7.

What the board does per feature release:

| Step | Board action | Where |
|---|---|---|
| 1 | New version (optionally "Plan with PM") | Roadmap page |
| 2 | Talk to the PM, then **Approve plan** | the anchor thread (comments + one card) |
| 3 | **Start** | Inbox card or Roadmap button |
| 4 | **Cut** | Inbox card ("1.3 is complete — cut now?") |
| 5 | Approve the go/no-go (gated projects) or **Confirm release** | Inbox (native approval) or card |
| 6 | **Start 1.4** | Inbox card |

A patch takes **Cut patch** and the go/no-go.

### 2.2 Definitions

- **Feature version.** The board's roadmap. Its tasks are **items**. A task without an item row is **Ongoing**, as in v0.1. Routine runs stay in the Routines band. The plugin never parks or counts either kind.
- **Anchor.** One per feature version, plus one standing anchor per fix-stream line.
  - The plugin creates it with `actor.actorUserId` set to the project's Roadmap owner (`board_user_id`), so it records `createdByUserId` and `responsibleUserId` for that owner (plugin-host-services.ts:1916-1932).
  - It is never assigned to a user. That is what makes notices unread for the owner: the owner's last touch is the creation time plus their own reads and comments (services/issues.ts:2926-2936).
  - Its origin stays plain `plugin:paperclip.roadmap`, so core leaves its successful-run lifecycle to the plugin (recovery/successful-run-handoff.ts:69-71, :507).
  - Its children inherit the owner as their responsible user (services/issues.ts:448-461). Agents' runs therefore get a real identity, including GitHub grants. Agents also see the version as their task's ancestor title (routes/issues.ts:8626).
- **Holder and turn.** The anchor is held by the **board** (unassigned) or by the **PM**, during a planning, reply or revise turn (assigned to the PM).
- **Parked.** Unassigned and in `backlog`. Nothing wakes a parked task:
  - no assignment wake (issue-assignment-wakeup.ts:43);
  - no comment wake, because comments wake only an assignee (issue-comment-wakeup.ts:1-27);
  - not a stranded-sweep candidate (recovery/service.ts:4500-4520);
  - not an orphan-recovery candidate, which takes only `todo` or `blocked` tasks (recovery/service.ts:2215-2240).

  The planned owner lives only in the item row.
- **Hand-out.** One plugin write, `{assigneeAgentId: planned owner, status: todo}`, followed by one pre-checked `requestWakeup`. It is the only way parked work starts.
- **Fix stream.** The project's one active **patch version** per line, for example `1.3.1`. It collects fixes and never completes on its own. A patch **Cut** turns it into a release and opens the next patch version on the same standing anchor.
- **Cut.** The board freezes a version's scope. This drafts the notes and creates the release task.
- **Release task.** A generated core task (`Release Acme iOS 1.3.0`, an ops item) for the release agent. It carries the checklist and the `release-record` document.
- **Late scope.** Items that join a version in `releasing` after its Cut: a QA failure fix, a triaged bug or a backport.
- **Carried fix.** A done stream fix that a feature Cut takes in (`carried_by`). It is **shipped** (`shipped_in`) only when a release that contains it is marked released.
- **Agent document.** The only channel from an agent to the plugin. It is markdown with exactly one fenced json block, written with `PUT /api/issues/:id/documents/:key`. The sandbox bridge allows that route (sandbox-callback-bridge.ts:175), and so does native `call_api` (native-runtime/runner-api-policy.ts:32-62). The plugin accepts a revision only from the expected writer (`updatedByAgentId` / `updatedByUserId`).
- **Board.** Active company members whose role is in `boardRoles` (default `owner`, `admin`). Every board verb also requires `actor.type === 'user'` and **no** `actor.runId`.

## 3. Lifecycles

### 3.1 Feature version (the roadmap)

```
            Approve plan (card or button)         Start                    Cut                    release complete
 draft ─────────────────────────────▶ planned ───────────▶ active ─────────────────▶ releasing ─────────────────────▶ released
   ▲ PM ⇄ board turns                  │ ▲ Revise plan       │ ▲ dev_complete flag      │ Reopen (board) ▲
   │                                   │ └ turns, re-approve │ └ cleared when work      ▼                │
   │                                   └── Start anyway (adopted or marker versions) ──▶ active ◀── releasing
 draft │ planned │ active ── Cancel (board, reason; unfinished work moved as at a Cut) ──▶ cancelled
```

**Release complete** means all of the following hold:

- a valid `release-record` exists and the release task is done;
- the board decided: an approved go/no-go that matches the record when the project has a publish gate (§5.4), otherwise a **Confirm release** card or button;
- no non-ops item of the version is open. If one is, the Release dialog moves it first.

| Transition | Trigger (who) | Preconditions | Side effects | Tasks moved to assigned todo |
|---|---|---|---|---|
| → draft | `version.create` with "Plan with PM" (board) | key unique in the project; PM invokable | row; anchor created unassigned `backlog` with the planning brief; anchor turn requested | 1 (the turn) |
| → planned (direct) | `version.create` without the PM, or `labels.adopt` (board) | — | row; anchor unassigned `backlog`; tasks join by move, marker line or adoption | 0 |
| draft → planned | plan approved (card or button; board) | latest valid `ready` revision; anchor board-held with no live PM run | plan tasks created parked under the anchor, 25 per call; eligible existing tasks parked, one write each; notice; Start card when no feature version of the project is active | 0 |
| planned → active | Start (card or button; board) | ≥ 1 item; no other active feature version unless `parallel` | `started_at`; anchor → `in_progress` (still unassigned); engine pass | ≤ 3 now, then ≤ 3 per minute |
| dev complete (flag) | reconcile (event or tick) | ≥ 1 item; 0 open items and sub-tasks (depth ≤ 8) | `dev_complete_at`, generation + 1; notice; Cut card | 0 |
| active → releasing | Cut (card or dialog; board) | every unfinished item has a target (§3.6) or the board waits | moves applied; stream's done fixes get `carried_by`; release version, tag, base tag and mode set; `release-notes` drafted; release task created parked under the anchor and requested; notice | 1 |
| releasing → active | Reopen (board) | the version is not yet released | `reopened_at`; release task re-parked unless in flight; older go/no-go approvals no longer count; notice | 0 |
| releasing → released | release complete (see above), or Mark released (board, reason) | record checks (§5.4); Mark released may override the version order with a reason | tag, sha, url, `released_at`; `shipped_in` set; anchor → `done`; stream re-based or opened; notices; Start card for the next planned version | 0 |
| → cancelled | Cancel (board, reason) | not releasing or released | items moved as at a Cut; open ops tasks cancelled; anchor → `cancelled` | 0 |

**Rules for every transition:**

- It is a compare-and-set on `row_version`, run under a per-company mutex.
- It writes an `events` row and `ctx.activity.log('roadmap.version.<verb>')`, because plugin action routes log nothing.
- A partial unique index allows only one active, non-parallel feature version per project.
- A board verb requires a user actor with a board role and no run id (§7.1).

### 3.2 Anchor: holder and status

| Version state | Held by the board (unassigned) | Held by the PM (a turn) |
|---|---|---|
| draft | `backlog` | assigned to the PM, `todo`, then `in_progress` after checkout |
| planned | `backlog` | PM, reply or revise turn |
| active, releasing | `in_progress` | PM, reply or revise turn |
| released | `done` (its pending cards expire, services/issues.ts:11149-11163) | — |
| cancelled | `cancelled` | — |
| stream anchor | always `in_progress` while the project is enabled | PM, reply or triage-question turn |

**Unassigned statuses.** While the anchor is unassigned, the plugin uses only `backlog` and `in_progress`:

- Neither is a candidate in any recovery query:
  - the stranded sweep needs an agent assignee or `in_review` (recovery/service.ts:4500-4520);
  - orphan recovery takes only unassigned `todo` or `blocked` tasks that have an agent creator (:2215-2240).
- Unassigned `in_review` is a sweep candidate. It is skipped only while it has no agent participant (:4599-4606), and it would show as a review with no path.

**Anchor drift.** Reconcile compares the anchor with `anchors.expected_status` and the holder.

- **An agent assigned, moved or closed it:** the plugin restores it in one write and posts a short note.
- **A board user did it:** the plugin does not undo the change. It sets `integrity = changed_by_user` and shows **Anchor changed — Restore** in Needs-you (`anchor.restore`). A closed anchor cannot take cards (issue-thread-interactions.ts:3589-3591), so notices for it wait, at most 10 attempts, until it is restored.

### 3.3 PM turns (slice P3)

| Event | From | To | Effect | Wakes |
|---|---|---|---|---|
| New version with the PM, or Revise plan | — / approved | drafting; turn requested | engine hands the anchor to the PM | 1 |
| Human comment on a board-held anchor (any open state) | board | turn requested (planning in draft, reply otherwise) | engine hands the anchor to the PM; a pending plan card is superseded by core (issue-thread-interactions.ts:4316-4356) | 1 |
| Human comment while the PM holds the anchor | PM | PM | core's own comment wake reaches the PM (issue-comment-wakeup.ts:1-27); the plugin only records it for the turn-end rule | 0 (core: 1) |
| Turn ends (rule below), plan `ready` and valid | PM | board | anchor → unassigned with the state's status; summary comment; plan card | 0 |
| Turn ends, plan `draft`, or a reply turn | PM | board | anchor → unassigned; comment quoting the PM's questions or reply | 0 |
| Turn ends, plan `ready` but invalid | PM | PM, at most twice per drafting episode | errors in `plan-check`; a third invalid end passes the anchor to the board with the errors | 1 |
| Request changes (card rejected with a reason, or button) | board | turn requested | anchor → PM with the reason | 1 |
| Approve plan (card accepted, or button) | board | approved | materialize (§4 step 3); the first approval moves draft → planned | 0 |

**Turn-end rule.** A PM turn ends only when all of the following hold:

1. The PM's latest run on the anchor (`holder_run_id`, or the newest run of that agent with `context_snapshot->>'issueId'` = the anchor) is terminal.
2. `heartbeat_runs` has no live successor. That means no run with `retry_of_run_id` equal to that run, and no run of the PM on the anchor in `queued`, `scheduled_retry` or `running`. These successors cover core's max-turn continuation, bounded retry and the fork's pool-account wait (heartbeat.ts:26750-26795). Core cancels each of them when the issue is reassigned (heartbeat.ts:16276-16289, 28936-28960).
3. At least one tick (≥ 30 s) has passed since the run finished, so that a deferred wake can be promoted first.
4. No human comment on the anchor is newer than the start of that run.
5. The anchor's `monitor_next_check_at` is null.
6. The run's `error_code` is not `operator_interrupted`. A board comment interrupt cancels the run and wakes the PM again with the comment (routes/issues.ts:7200-7215).

If a condition fails, `holder_run_id` follows the successor and the plugin waits. The turn ends with a failure note and a `stalled` notice in either of these cases:

- the latest run failed and nothing was scheduled within 2 ticks;
- core moved the PM-held anchor to `blocked`, which its unsuccessful-run recovery can do (recovery/service.ts:5551-5590).

**Bounce rule.** Bounces are counted per drafting episode, that is, since the anchor last passed to the board, not per document revision, because each save creates a new revision (documents.ts:361-386).

**Card rule.** The plan card is the only card with `supersedeOnUserComment`.

### 3.4 Fix stream and patch versions (slice P2)

```
 open: at the project's first feature release, or board `stream.open {key, base}`
 active (collecting); key = next patch of the latest release on the line (1.3.1); standing anchor `Fixes: Acme iOS`
   │ joins: PM's `roadmap-fixes` · top-level type:bug tasks (untriaged) · board Report bug · board move
   │ feature Cut: done, unshipped stream fixes get carried_by = that feature version (they are on main)
   │ feature Released: carried fixes get shipped_in and move into the feature version; the stream re-bases
   │                   (1.3.2 → 1.4.1) unless the board keeps old lines (per-line mode, P4)
   │ ≥ patch_suggest_at done unshipped fixes, or one done blocker → notice + `Cut patch 1.3.1?` card
   │ Cut patch (board; ≥ 1 done fix with shipped_in NULL; no other patch of the line releasing)
   ▼
 releasing 1.3.1 (done unshipped fixes only, including fixes carried by an unreleased feature version)
   ── release complete │ Mark released ──▶ released (shipped_in = 1.3.1)
 + a new patch version 1.3.2 opens on the same anchor and receives every open fix (in-flight fixes keep running)
```

**Rules:**

- **Fixes are daily work and are not held.** A fix with an owner is handed out at once: critical fixes and backports first and outside WIP, within the shared budget.
- **Shipped tasks never move.** A done item of a released version that reopens stays in its version. Core reopens a done, agent-assigned task on any human comment (routes/issues.ts:2278-2322), so a reopen is not evidence of a bug. The plugin flags it on the stream anchor; a new fix that is related to it is filed by Report bug or by the PM.

### 3.5 Release task (both kinds)

1. Created parked under the anchor, with the planned owner set to the release agent.
2. Handed out at the Cut (1 wake).
3. Optional `candidate` record.
4. Go/no-go: one `request_board_approval` linked only to the release task, with the roadmap marker in its payload (§5.4). The task waits in `in_review`, which a linked pending approval allows (routes/issues.ts:2008-2019).
5. Approved: the approve wake reaches the requester (routes/approvals.ts:359-385).
6. Tag, deploy, write `release-record` (stage `released`), mark the task done.
7. The plugin validates, then completes the release (§3.1).

**When the path breaks:**

- **Revision requested** on the go/no-go wakes nobody in core (routes/approvals.ts:477-502). The plugin sees `approval.decided` and hands the task back to the release agent (1 wake) with the note.
- **Late scope** (§5.1) gets a comment on the release task. When all of it is done and the task is not in flight, the plugin hands the task back to the release agent (1 wake).
- **Invalid record:** the plugin reopens the task once to the release agent with the errors (1 wake). A second invalid finish puts **Accept as released / Send back** in Needs-you.
- **Release task cancelled** while the version is `releasing`: notice **Release aborted**, plus Needs-you **Reopen or recreate the release task**.
- **Reopened by a comment** after the version was released: the plugin replies "already released; do not repeat any step" (checklist step 0).

### 3.6 Item inside a version

```
parked ──hand-out: version started · blockers done|cancelled · owner invokable · no budget block · WIP free · bucket left──▶
assigned todo ──core──▶ in_progress / in_review / blocked ──core──▶ done │ cancelled
released by core (POST /release → unassigned todo, services/issues.ts:11941-11958) ──reconcile──▶ re-parked, then handed out again
moves (Cut, Cancel, Release dialog, board move, triage):
  → a draft/planned version: one write parks it, unless in flight ("carried in flight") or already done/cancelled
  → a started version or the stream: membership only, no task write
  → Ongoing: hand out to the chosen owner now, or leave unassigned in the project backlog for the PM
drift: an item of a draft/planned version that is assigned or out of backlog (not carried in flight, not done/cancelled) → flag + Re-park
```

**When an item is "in flight":** it is `in_progress` or `in_review`, or has a live checkout or execution run, or was handed out in the last 10 minutes.

**Every move:**

- **Keeps dependencies whole.** Dependents left behind are moved too, or the board drops the edge in the dialog (`issue.relations.write`), or the move is refused. A dependent that stays behind a moved, unfinished blocker can never be handed out, because `requestWakeup` refuses open blockers (plugin-host-services.ts:2175-2181).
- **Rewrites the task's first line** (`Roadmap-Version: …`) and its footer in one description-only write.

## 4. End-to-end flow

**Wake accounting.** Every wake below counts as a task moved to assigned `todo`, or as an explicit wake, against one budget per company. The budget is at most `handoutsPerMinute` (≤ 3) per rolling 60 s, persisted as `events` rows. Core runs on anchors that the plugin did not request also count against it (§6.6).

The steps describe the finished flow, and each names the slice that delivers it.

**0. Enable (once per company and per project), P1**

- **Actor:** instance admin, then board.
- **Company:** the instance admin opens Instance settings → Plugins → Roadmap, picks the company and saves `{enabled: true, boardRoles}`, which is a `plugin_config` row. The save refreshes the worker's proactive company scope live (routes/plugins.ts:2372-2383), and the worker receives the config through `onConfigChanged` (`multiCompanyConfig: true`).
- **Project:** the board opens the project tab → Settings (`project.updateSettings`) and sets:
  - the **Roadmap owner** (required; defaults to the user saving the settings);
  - the PM (default `projects.lead_agent_id`);
  - the release agent (default the PM);
  - tag pattern, release procedure, publish gate, review route and WIP.
- **Acme:** `labels.adopt` turns the existing `v:` label versions into rows, anchors and items. The planned owner and rank come from `Planned-Owner:` / `Rank:` lines (matched without case; a space instead of the hyphen is accepted), or else from the current assignee. The board confirms each suggested state.
- **Wakes:** 0.
- **Board sees:** write controls, lanes with stored states, and one anchor per version in Mine.

**1. Create the roadmap, P3 (P1: without the PM)**

- **Actor:** board.
- **Mechanism:** Roadmap → project → **New version** {key 1.3, goal, target, Plan with PM}. `version.create` writes the row in `draft` and creates `Roadmap: Acme iOS 1.3`:
  - with `actorUserId` = the Roadmap owner, unassigned, `backlog`;
  - with the planning brief as its description and origin `plugin:paperclip.roadmap`;
  - and requests the PM's first turn. The engine assigns the anchor to the PM in `todo` and sends one `requestWakeup`.
- **Wakes:** 1.
- **Board sees:** lane `1.3 · Draft · planning with PM`, and the anchor in Mine.
- **Before P3:** the version starts `planned`, and planning follows the interim convention (§9.4).

**2. Plan with the PM in turns, P3**

- **Actors:** PM, then board.
- **PM, in its run on the anchor:**
  1. Reads the brief and the newest comments.
  2. Saves `version-plan`.
  3. Reads `plan-check`, which the plugin rewrites within seconds of each save (needs S12).
  4. Asks any questions in one comment.
  5. Ends the run without touching the anchor's status or assignee.
- **Plugin:**
  - When the turn-end rule (§3.3) holds, the plugin unassigns the anchor (status `backlog`) and posts one summary comment.
  - If the plan says `ready` and validates, it also posts the plan card. This is a `request_confirmation` that targets the `version-plan` revision (validators/issue.ts:1494-1503), with `human_only`, continuation `none` and `supersedeOnUserComment`.
  - A board reply comment requests the next turn.
- **Wakes:** 1 per board reply or Request changes.
- **Board sees:** the anchor unread on each turn, and a Plan review view with tasks, owners, dependencies, the diff against the last approved revision, and warnings.

**3. Prepare the tasks (parked), P3**

- **Actor:** board.
- **Mechanism:** the board accepts the plan card or presses **Approve plan**. The plugin finds card outcomes by polling `listInteractions`, because interaction resolution emits no plugin event (activity-log.ts:15-28). The materializer then creates the plan tasks in dependency order, 25 per call:
  - parked: status `backlog`, no assignee, no actor agent;
  - with `blockedByIssueIds`, priority, and parent = the anchor or a plan group (or an epic that has a responsible user);
  - with the first line `Roadmap-Version: <id> · Acme iOS 1.3 · plan key <k>`, then the description, the acceptance criteria and the footer (§9.5);
  - with origin `plugin:paperclip.roadmap:work` and originId `plan:<versionId>:<key>`.

  Each task gets an item row with the planned owner, rank and review flag. Eligible existing tasks are parked in one write each. The version moves to `planned` and the notice reads "Plan applied: 16 parked". A Start card follows if no feature version of the project is active.
- **Wakes:** 0. The tasks have no assignee, and plugin writes trigger no route wakes (plugin-host-services.ts:1916-1988).
- **Board sees:** `1.3 · Planned · 16 parked`.

**4. The board starts, P1**

- **Actor:** board, whenever it wants.
- **Mechanism:** the board accepts the Start card or presses **Start**.
  - `version.start` does a compare-and-set planned → active and moves the anchor to `in_progress` (still unassigned).
  - The engine (§7.6) then hands out ready items: one write and one `requestWakeup` each, with key `roadmap:handout:<issueId>:<n>`.
- **Wakes:** ≤ 3 now, then ≤ 3 per minute as owners' slots free up.
- **Board sees:** `In development 0/16 · 3 handed out`.

**5. Develop, P1**

- **Actors:** engineers, QA, PM.
- **Mechanism:**
  - The normal core flow applies. Hand-backs are `todo` + PM (Board policy), and review and merge stages work as configured (with S5).
  - Each freed slot (a task leaving `todo` / `in_progress`) leads to the next hand-out, triggered by a debounced reconcile or the 60 s timer.
  - Bugs go under Proposals, and the PM files them with `roadmap-fixes` (daily fix path).
  - A marker-line task joins the version only when the PM or a board member created it, and it is then flagged "added after Start".
- **Wakes:** 1 per hand-out.
- **Board sees:** progress; parked and needs-owner counts; drift and stall flags in Needs-you.

**6. Development complete, P1**

- **Actor:** plugin.
- **Mechanism:** the last item or sub-task closes, which triggers a reconcile. The completion query reaches 0 open with ≥ 1 item. The plugin then:
  - sets `dev_complete_at` and a new generation;
  - posts a notice on the anchor with counts and a `[@Owner](user://<id>)` mention, which brings an archived anchor back (services/issues.ts:3044-3060);
  - adds the **Cut 1.3 now?** card (P2);
  - logs `roadmap.version.dev_complete`.
- **Wakes:** 0.
- **Board sees:** the anchor unread, inbox badge +1, lane Complete, Needs-you "Cut 1.3".

**7. Cut the release, P2**

- **Actor:** board.
- **Mechanism:** the board accepts the Cut card, whose defaults are release version 1.3.0, carry the stream's done fixes, and nothing unfinished. Or it opens the Cut dialog and chooses a target per unfinished item:
  - an in-flight item goes to a started version, the stream, Ongoing, or a planned version as "carried in flight";
  - other unfinished items go to the next version (re-parked), the stream, or Ongoing.

  `version.cut` then:
  - moves the version to `releasing` and sets `carried_by` on the stream's done, unshipped fixes;
  - sets tag `v1.3.0`, the base tag (the previous release on the line) and the mode hint (§5.2);
  - drafts `release-notes`;
  - creates `Release Acme iOS 1.3.0` parked under the anchor, with the release agent as planned owner, and requests its hand-out;
  - posts a notice whose wording follows the hand-out result ("handed to ReleaseEngineer", or "waiting: ReleaseEngineer is paused").
- **Wakes:** 1.
- **Board sees:** lane Releasing, with a link to the release task.

**8. DevOps release, P2**

- **Actor:** release agent.
- **Mechanism:** the release agent follows the checklist (§5.5):
  1. Scope check against git, the changelog, build, CI and the candidate.
  2. With a publish gate, one `request_board_approval` linked only to the release task, carrying `roadmap: {versionId, releaseVersion, tag, sha}`. The task moves to `in_review` and the run ends.
  3. Tag, `gh release create --verify-tag`, deploy, verify.
  4. `release-record` with stage `released`.
  5. Task done.
- **Wakes:** 1, plus 1 when the approval is decided.
- **Board sees:** the approval in every board member's Inbox (ui/src/lib/inbox.ts:803-808), and "Release candidate ready" on the anchor.

**9. Released, P2 (P1: Mark released)**

- **Actor:** plugin.
- **Mechanism:** when the release task is done, the plugin validates the record (§5.4):
  - **Valid, gate on:** a matching board-decided approval → **released**.
  - **Valid, gate off:** a **Confirm release 1.3.0?** card; acceptance → released.
  - **Invalid:** the release task reopens once with the errors.

  On release:
  - tag, sha and url are stored;
  - `shipped_in` is set on the members and on carried fixes, and carried fixes move into 1.3;
  - the anchor goes to `done`;
  - the stream re-bases;
  - the notice reads "Released 1.3.0 — v1.3.0 @ abc1234 · notes";
  - the next planned version's anchor gets "1.4 is ready to start: 12 parked" plus a Start card.
- **Wakes:** 0, or 1 when the record is invalid.
- **Board sees:** unread notices, the Releases list, Needs-you "Start 1.4".

**10. Next roadmap.** The board accepts "Start 1.4" (step 4). Steps 1-3 for 1.4 can run while 1.3 is still active or releasing.

**Daily fix path (summary; details in §5.1), P2**

| Step | What happens | Wakes |
|---|---|---|
| F1 Found | Engineers and QA write the bug under Proposals (`Affects: … · Severity: …`). The board can use Report bug, and any agent or board user can create a `type:bug` task in core | 0 |
| F2 Filed | The PM writes `roadmap-fixes` on the task it holds. The plugin creates `Bug: …` tasks under the target's anchor, hands out those with owners, and replies once on that task | 1 per hand-out |
| F3 Triage | Untriaged fixes wait at most 30 minutes, or none for a blocker. Then the plugin creates `Triage fixes: Acme iOS (3)` for the PM (at most one open), and the PM decides with `roadmap-fixes` | 1 per batch |
| F4 Work | Normal daily work. The PR title ends with `(<ID>)` and the PR merges to main | — |
| F5 Accumulate | The stream stays active. A threshold notice and card suggest a patch | 0 |
| F6 Cut patch | The board accepts the card. The patch goes to `releasing`, the next patch opens, the mode is computed and the release task is created; then steps 8-9 | 1 |
| F7 Ride a feature release | A feature Cut carries the stream's done fixes. They ship with it, unless a patch ships them first | 0 |

**Board decisions per cycle.** A feature release takes New version, Approve plan, Start and Cut, plus the planning conversation and either the go/no-go or Confirm release. A patch takes Cut patch plus the same release decision.

## 5. Fix stream and releases (DevOps)

### 5.1 How fixes join, and when they ship

- **Joining.**
  - The PM files fixes with `roadmap-fixes` (target `stream`, `version:<key>` or, for kind `backport`, `version:<releasing patch>`).
  - Board Report bug.
  - Board moves.
  - Top-level `type:bug` tasks in enabled projects (created in core by anyone) join the stream **untriaged**. Untriaged fixes are never handed out; they only feed the PM's triage task. Labels are visible on task rows (services/issues.ts:3266-3283).
- **Late scope.** A version in `releasing` accepts only `bug` and `backport` items (QA failures, triaged bugs of the version being released, backports). Each join posts a comment on the release task, with no wake. When every late-scope item is done and the release task is not in flight, the plugin hands the release task back to the release agent (1 wake). The record must list the done late-scope items in `includedIssueIds`, or the board accepts the gap.
- **Carried and shipped.**
  - A feature Cut sets `carried_by` on the stream's done fixes that have `shipped_in` NULL.
  - **Shipped** is set only when a release is marked released: on its members, its late scope, its carried fixes and fixes it lists in `includedIssueIds`.
  - A patch can still ship a fix that an unreleased feature version carries: the fix is done, unshipped and on main. In that case the fix ships first in the patch and is listed again in the feature version's notes under "Included from fixes".
  - At a feature release, fixes it carried that were still unshipped move into the feature version, so the stream holds only unshipped fixes.
- **Version order** is checked per **line**: `major.minor` of the release version.
  - A patch must be above the last release of its own line; a feature release must be above every release of the project.
  - So patch 1.3.1 can ship after 1.4.0, which is common while a store review is pending.
  - `version.markReleased` takes an explicit override with a reason.
- **Patch Cut preconditions:** ≥ 1 done fix with `shipped_in` NULL, and no other patch of the same line in `releasing`.

### 5.2 Git strategy

The plugin stays out of git. It computes a mode hint and writes it into the release task, and the release agent confirms it with git and records what it did.

- **Trunk and tags.** Every repo has one trunk (`main`). Releases are annotated tags rendered from the project's `tag_pattern`: `v{version}`, or `api/v{version}` in a monorepo.
  - No release branch is ever pushed, and tags are never moved; a wrong tag is superseded by a patch (rev5 R4, §11.1).
  - Every fix merges to main first, as daily work.
  - The only extra refs are non-branch refs: `refs/roadmap/rc/<version>/<n>` for candidates (rev5 §6.3) and `refs/roadmap/backport/<version>/<ID>` for backports.
- **Feature release:** from main, at the candidate sha the release agent picks, normally the build that passed QA.
- **Patch release, `release_mode` computed at the Cut.** The mode is `cherry_pick` when any of these holds, and `from_main` otherwise:
  1. a release on this line since the last feature release was cherry-picked, so its tag is not on main;
  2. any feature version of the project that is active, releasing, or cancelled since the base release has a done item;
  3. any done Ongoing task of the project finished after the base release.

  The release agent confirms the hint with `git merge-base --is-ancestor <baseTag> origin/main` and `git log --first-parent <baseTag>..origin/main`. For `from_main`, every commit in the range must map to a stream fix by its `(<ID>)` suffix.

  The `cherry_pick` steps:
  1. `git fetch --tags`
  2. `git checkout --detach <baseTag>`
  3. `git cherry-pick -x <merge sha>` for each fix, oldest first
  4. build and test
  5. optionally push `refs/roadmap/rc/<version>/<n>`
  6. `git tag -a v1.3.1 <sha> -m 'Acme iOS 1.3.1'`
  7. `git push origin v1.3.1`
- **Backports.** A conflict the release agent cannot resolve trivially stops that fix:
  1. The release agent hands the release task back to the PM (todo + PM) with the Proposal "Backport `<fix>` onto `<baseTag>`".
  2. The PM files it with `roadmap-fixes` (`kind: backport`, `target: version:1.3.1`, `relatedIssue`).
  3. The plugin creates `Backport: … → 1.3.1` under the stream anchor (critical, outside WIP) with the backport footer (§9.6). The footer says: no PR to main and no branch; push the commit to `refs/roadmap/backport/1.3.1/<ID>`.
  4. When every backport of the patch is done, the plugin hands the release task back to the release agent (1 wake).

  The board can choose fix-forward instead (move the fix to the next feature version).

### 5.3 Release notes

- **Draft, once, at the Cut.** The plugin writes `release-notes` on the feature anchor, or `release-notes-1-3-1` on the stream anchor, because document keys allow no dots (validators/issue.ts:1164-1170). It is a core document, so it is exported with the company:

  ```
  # Acme iOS 1.3.0 — draft
  Base v1.2.1 · Mode from main · Cut by <user> on 2026-11-03
  ## Features (14)                 - Login with passkeys (ACM-140)
  ## Fixes (3)                     - Crash when opening settings offline (ACM-151) · affects 1.2.0
  ## Included from fixes (2)       - ACM-301, ACM-302 (also in 1.2.2 if that patch ships first)
  ## Moved out (2) · Not included
  ## Known issues                  - open bugs whose affects is 1.3
  ```
- **Enrichment, by the release agent:**
  - `git log --no-merges --format='%H%x09%s' <baseTag>..<sha>`, grouped by conventional-commit type;
  - up to 3 "What Changed" bullets per `(#N)` PR, via `gh pr view N --json title,body,url`. This is the algorithm of `scripts/draft-stable-notes.sh`. The plugin cannot read work products, so PR links are the agent's job.
  - three reconcile lists: code tasks with no commit in the range; commits with no task id; stream fixes on main that are missing from a cherry-pick candidate.
- **No automatic overwrite.** The plugin never rewrites existing notes. **Regenerate** is a board action that warns that edits are lost, and it uses a guarded write with `baseRevisionId` (S12). Without S12, core answers 409 to any update (documents.ts:349-358). A re-Cut after Reopen keeps the existing notes and posts the scope delta as a comment.

### 5.4 The release record and the board's go/no-go

**The record.** `release-record` (schema `paperclip.roadmap/release-record@1`) lives on the release task. Its fields are: stage (`candidate` | `released`), version, mode, baseTag, tag, sha, url, ciRun {url, conclusion}, buildRef, deployments[] {env, startedAt, finishedAt, result, url}, qa {verdict, reportIssueId}, rollbackRef, publishApprovalId, includedIssueIds[], unattributedCommits[], missingFromCandidate[], baseIsAncestorOfMain, nonStreamCommits[].

**Validation at stage `released`:**

- The writer is the release task's assignee, or a board user.
- `sha` is 40 hex characters.
- `tag` equals the rendered pattern and is unique in the project; a partial unique index enforces this too.
- `version` is semver, and it is above the last release of its **line**, or above every release for a feature version, using v0.1's `compareVersionKeys`.
- `mode` equals the hint, or the record says why not. For a patch, `nonStreamCommits` is empty, and `baseIsAncestorOfMain` is true when `mode = from_main`. Otherwise the board accepts the record.
- `includedIssueIds` contains every done late-scope item.
- With the QA chain, the verdict is pass. If deployments are listed, the last one succeeded.
- With `requires_tag = false` (a build-only milestone, such as an MVP shipped only to a beta channel), tag and sha are optional and `buildRef` is required.

**The board's decision.**

- **Gate on.** `publishApprovalId` must meet all of these:
  - it is a `request_board_approval` that is `approved`;
  - it is linked to the release task through `issue_approvals`;
  - it was created after the latest Cut or Reopen;
  - its payload carries `roadmap: {versionId, releaseVersion, tag, sha}` matching the record, because the payload is otherwise free-form (validators/approval.ts:5-10);
  - it was decided by a user whose active role is in `boardRoles` (`approvals.get` → `decidedByUserId` → `access.members.list`). Core lets any non-viewer approve (routes/approvals.ts:294-300; routes/authz.ts:104-119);
  - it has not been used by another release (`versions.publish_approval_id` is unique per project).
- **Gate off.** A valid record raises a **Confirm release** card, or the board presses the button, so the release agent can never complete a release alone.

**Evidence and commands.** Verification commands the agent pastes:

- `git ls-remote --tags origin <tag>` (the sha must match);
- `gh release view <tag>`;
- the project's health or version check;
- for mobile, the store or beta-channel state.

The evidence is self-reported, not verified against GitHub; a verifier is a later option.

### 5.5 Release task checklist

This is the generated description of `Release Acme iOS 1.3.0`: an ops item with origin `:work`, a child of the anchor, handed to the release agent.

```
Inputs: version 1.3.0 · tag v1.3.0 · base v1.2.1 · mode from_main (hint; rule in the Roadmap help) · notes: ACM-150 › release-notes
Tasks (16): ACM-140 … · carried fixes (2): ACM-301, ACM-302 · procedure: <project release_procedure>
0. If the Roadmap's latest comment here says the version is already released, repeat no step: answer and mark done.
1. Scope: git fetch --tags; git log --no-merges v1.2.1..<sha>; map commits to task ids by the (ACM-n) suffix; fix
   release-notes; list unattributed commits. Confirm the mode and say why
   (git merge-base --is-ancestor v1.2.1 origin/main; git log --first-parent v1.2.1..origin/main).
2. Changelog: if the repo keeps CHANGELOG.md, prepend the notes in a normal PR merged before you pick the candidate
   (cherry_pick mode: commit it on the detached candidate).
3. Build and verify per the procedure; record the CI run and build ref. Optional: write release-record, stage candidate.
4. Go/no-go (publish gate on): file ONE request_board_approval with issueIds [this task] only and payload
   {"title": "Publish Acme iOS 1.3.0 v1.3.0 @ <sha7>", "roadmap": {"versionId": "<id>", "releaseVersion": "1.3.0",
   "tag": "v1.3.0", "sha": "<40-hex>"}, summary, notes link, CI link, unattributed changes, risks, rollback}.
   Set this task in_review; end the run. Approval wakes you; a rejection or revision request comes back with its note.
   If the sha changes later, file a new approval.
5. Tag: git tag -a v1.3.0 <sha> -m 'Acme iOS 1.3.0'; git push origin v1.3.0; no branch.
   gh release create v1.3.0 --verify-tag --title 'Acme iOS 1.3.0' --notes-file notes.md
6. Deploy or submit per the procedure; verify (git ls-remote --tags origin v1.3.0; health or store state).
7. Record: write release-record (stage released, all fields, includedIssueIds). Mark this task done.
If anything fails: hand back to the PM (todo + PM) with the error; never move a tag. A cherry-pick conflict goes under
Proposals as 'Backport <fix> onto <base tag>'.
```

### 5.6 Release QA chain (P4, opt-in per project)

When `release_steps = candidate_qa_publish`, which suits Acme iOS with its store beta channel (rev5 R10), the Cut creates three chained, parked tasks:

- `· candidate` for the release agent: steps 1-3;
- `· QA` for the QA agent, blocked by the candidate;
- `· publish` for the release agent, blocked by QA: steps 4-7.

The engine hands out each step when its blocker is done, so each completion costs exactly one wake. On a QA FAIL, the PM files the fixes into the releasing version as late scope. When they are done, the plugin reopens the candidate step and re-parks QA.

### 5.7 Changelog per project

- The **Releases** list in the Release desk: key, kind, tag, sha7, date and notes link for every released version.
- Each anchor's `release-notes` documents.
- `roadmap.changelog` as markdown or JSON, with a Copy button, newest first.
- The repo's `CHANGELOG.md`, through checklist step 2.

## 6. Data model

### 6.1 Namespace and SQL rules

- **Namespace:** `plugin_roadmap_d0dfaa84c1`, derived from slug `roadmap` plus sha256('paperclip.roadmap')[0:10] (server/src/services/plugin-database.ts:31-44).
- **One migration.** `migrations/001_roadmap.sql` creates every table P1-P4 need, so every later slice ships as a code-only swap. Every enum is complete in 001 (rev5 §13 rule 3).
- **Migration validator** (plugin-database.ts:191-244):
  - DDL and namespace backfills only;
  - schema-qualified names;
  - no DROP, DELETE, functions or triggers;
  - `public.*` only as `FROM` / `JOIN` / `REFERENCES` of whitelisted tables;
  - rev5 §13 rule 4 (no comment naming a public table, nothing after the last `;`, no `SET`).
- **Foreign keys into public:** only `company_id → public.companies ON DELETE CASCADE`, as the fork's sandbox provider plugin does. No foreign key reaches issues, agents or projects, so:
  - activation takes no lock on `public.issues`;
  - plugin rows never block a core delete;
  - the timer prunes rows whose task or project is gone.

  Columns whose internal foreign key is `ON DELETE SET NULL` carry no CHECK and no NOT NULL (rev5 §13 rule 5).
- **Company scoping:**
  - Every write takes `company_id` from the host context, and every read of `public.*` filters `company_id`.
  - Reads of items also filter `hidden_at`. **Blocker** joins do not, because core counts hidden open blockers (services/issues.ts:7310-7330).
  - `ctx.db.query` text must avoid the whole words insert, update, delete, alter, create, drop and truncate (plugin-database.ts:261-262).
  - `ctx.db.execute` may reference only the namespace (:277-300).
- **List parameters** are passed as JSON text (`$2::jsonb`), never as arrays. `bindSql` turns an array into `($2, $3)` (plugin-database.ts:303-325; drizzle `sql.js:93-103`).

### 6.3 Per-company config row

An instance admin saves the row through the auto-form generated from `instanceConfigSchema`. It holds:

- `enabled` (default false: the company keeps v0.1's read-only behaviour);
- `boardRoles` (default `['owner','admin']`);
- `handoutsPerMinute` (1-3, default 3);
- `stalledHours` (default 4);
- `chatWebhook` (secret ref, P4).

The same row gives the worker its proactive scope for the company (plugin-worker-manager.ts:2667-2693). The plugin declares `multiCompanyConfig: true`, so `onConfigChanged` accepts every company. Without it the SDK rejects the second company with `CROSS_TENANT_CONFIG` (worker-rpc-host.ts:1876-1895).

### 6.4 Where membership truth lives: plugin rows (`items`), not labels

1. **Labels are fragile.** Any actor with company access can delete one, and the delete cascades. A `labelIds` write replaces the whole set (routes/issues.ts:8366-8417; services/issues.ts:7278-7295).
2. **The plugin cannot create labels or learn new label ids.** `labels` and `issue_labels` are not core-read tables (packages/shared/src/constants.ts:1440-1454).
3. **Agents on remote devices have no labels route.** The bridge allowlist has none (sandbox-callback-bridge.ts:125-231).
4. **Rows join `public.issues` in one SQL statement.** Counts are exact, with no SDK paging and no double offset.
5. **Rows carry what labels cannot:** planned owner, rank, review flag, triage, severity, affects, carried_by, shipped_in.

Labels stay optional. They are the import source for v0.1 label versions (`labels.adopt`) and, in P4, an opt-in mirror for core-list filtering.

Rows are not exported with a company. The history still survives in core data:

- the anchors' documents;
- the parent links of version tasks to their anchor;
- the `Roadmap-Version:` first line of every member task.

### 6.5 Agent documents (core documents the plugin reads)

**Format.** Each document is markdown with exactly one fenced json block. Every revision is processed once (`doc_inbox`), and only from the expected writer. Rejections are reported in `plan-check`, or in one comment for the other documents.

- **`version-plan` on the anchor** (schema `paperclip.roadmap/version-plan@1`), written by the version's PM or a board user.
  - **Why not `plan`:** the key is deliberately not `plan`. Core's plan-confirmation logic, the accepted-plan continuation and the rejection wake all match only `key === 'plan'` (routes/issues.ts:851-854), while the document-target staleness check works for any key (issue-thread-interactions.ts:1725-1830).
  - **Fields:**
    - `status`: `draft` | `ready`;
    - `version`: {key, goal, target};
    - `tasks[]`: {key, title, description, acceptance[], kind: feature | bug | chore | group, owner (agent name or id), rank, priority, dependsOn[], parent (plan key), epic (issue identifier), review (bool)};
    - `existing[]`: {issue, action: include | leave, owner, rank};
    - `questions[]`.
  - **Validation:**
    - 1-200 tasks, with unique keys matching `^[a-z0-9][a-z0-9-]{0,47}$`;
    - owners resolve to company agents that are not terminated (a warning if paused or in error);
    - `dependsOn` and `parent` resolve and form no cycle;
    - an epic resolves within the project;
    - existing tasks belong to the project and to no other open version unless parked there; an in-flight existing task gets the warning "joins as is".
- **`roadmap-fixes` on any task of an enabled project** (schema `paperclip.roadmap/fixes@1`), written by the project's PM or a board user.
  - `fixes[]`: {key, kind: fix | backport, title, description, severity, affects, target: `stream` | `version:<key>`, owner, priority, relatedIssue}, at most 20 new per revision, idempotent per (task, key);
  - `triage[]`: {issue, target: `stream` | `version:<key>` | `ongoing`, owner, priority, reason}.
- **`release-record` on the release task** (§5.4).
- **`qa-report` on the QA chain task** (P4): verdict pass | fail, plus evidence.

### 6.6 Key queries

Each is one SELECT or WITH statement through `ctx.db.query`. Together they read the whitelisted tables `companies`, `projects`, `agents`, `issues`, `issue_relations`, `issue_documents`, `issue_comments`, `heartbeat_runs`, `approvals`, `issue_approvals` and `budget_incidents`.

```sql
-- completion per version: items (not ops) and their sub-tasks to depth 8, each issue counted once
WITH RECURSIVE t AS (
  SELECT i.version_id, x.id, x.status, 0 AS depth
  FROM plugin_roadmap_d0dfaa84c1.items i
  JOIN public.issues x ON x.id = i.issue_id AND x.company_id = $1 AND x.hidden_at IS NULL
  WHERE i.company_id = $1 AND i.kind <> 'ops'
    AND i.version_id IN (SELECT (jsonb_array_elements_text($2::jsonb))::uuid)
  UNION ALL
  SELECT t.version_id, c.id, c.status, t.depth + 1
  FROM t JOIN public.issues c ON c.parent_id = t.id AND c.company_id = $1 AND c.hidden_at IS NULL
  WHERE t.depth < 8)
SELECT version_id,
       count(DISTINCT id) FILTER (WHERE depth = 0) AS items,
       count(DISTINCT id) FILTER (WHERE depth = 0 AND status = 'done') AS done,
       count(DISTINCT id) FILTER (WHERE status NOT IN ('done','cancelled')) AS open
FROM t GROUP BY version_id;

-- hand-out candidates: unserved explicit requests plus parked items of started versions
-- (blocker = issue_relations.issue_id, blocked = related_issue_id; services/issues.ts:7310-7330)
SELECT i.issue_id, i.version_id, i.kind, i.ops_role, i.planned_owner_agent_id, i.rank, x.priority, x.status,
       v.state, v.started_at, i.handout_requested_at,
       NOT EXISTS (
         SELECT 1 FROM public.issue_relations r
         JOIN public.issues b ON b.id = r.issue_id AND b.company_id = $1          -- hidden blockers still count
         WHERE r.company_id = $1 AND r.type = 'blocks' AND r.related_issue_id = i.issue_id
           AND b.status NOT IN ('done','cancelled')) AS blockers_resolved
FROM plugin_roadmap_d0dfaa84c1.items i
JOIN plugin_roadmap_d0dfaa84c1.versions v ON v.id = i.version_id AND v.company_id = $1
JOIN public.issues x ON x.id = i.issue_id AND x.company_id = $1 AND x.hidden_at IS NULL
WHERE i.company_id = $1
  AND (i.handout_backoff_until IS NULL OR i.handout_backoff_until < now())
  AND ( (i.handout_requested_at > coalesce(i.handed_out_at, '-infinity'::timestamptz)
         AND v.state IN ('active','releasing'))
     OR (x.status = 'backlog' AND x.assignee_agent_id IS NULL AND x.assignee_user_id IS NULL
         AND i.planned_owner_agent_id IS NOT NULL AND i.kind NOT IN ('group','ops')
         AND coalesce(i.triage, 'accepted') <> 'untriaged'
         AND (v.state = 'active' OR (v.state = 'releasing' AND i.kind IN ('bug','backport')))) );
-- two sibling queries serve anchor turns (anchors.turn_requested_at > coalesce(turn_handed_at, '-infinity'))
-- and Ongoing hand-outs (items.version_id IS NULL)

-- wake bucket: plugin hand-outs and wakes, plus core runs on anchors that the plugin did not request
SELECT (SELECT count(*) FROM plugin_roadmap_d0dfaa84c1.events e
         WHERE e.company_id = $1 AND e.kind IN ('handout','wake') AND e.created_at > now() - interval '60 seconds')
     + (SELECT count(*) FROM public.heartbeat_runs r
         JOIN plugin_roadmap_d0dfaa84c1.anchors a
           ON a.company_id = $1 AND a.issue_id::text = r.context_snapshot->>'issueId'
         WHERE r.company_id = $1 AND r.created_at > now() - interval '60 seconds'
           AND NOT EXISTS (SELECT 1 FROM plugin_roadmap_d0dfaa84c1.events w
                            WHERE w.company_id = $1 AND w.kind IN ('handout','wake') AND w.issue_id = a.issue_id
                              AND w.created_at > now() - interval '120 seconds')) AS used;

-- invocation-block mirror before a hand-out (budgets.ts:745-860): $1 company, $2 project, $3 owner agent
SELECT (SELECT status FROM public.companies WHERE id = $1) AS company_status,
       (SELECT paused_at IS NOT NULL AND pause_reason = 'budget' FROM public.projects
         WHERE id = $2 AND company_id = $1) AS project_budget_paused,
       (SELECT status FROM public.agents WHERE id = $3 AND company_id = $1) AS agent_status,
       EXISTS (SELECT 1 FROM public.budget_incidents bi
                WHERE bi.company_id = $1 AND bi.status = 'open' AND bi.threshold_type = 'hard'
                  AND ((bi.scope_type = 'company' AND bi.scope_id = $1)
                    OR (bi.scope_type = 'project' AND bi.scope_id = $2)
                    OR (bi.scope_type = 'agent' AND bi.scope_id = $3))) AS hard_stop_open;

-- turn-end successors (§3.3): $2 PM agent, $3 anchor id as text, $4 holder run id
SELECT r.id, r.status, r.error_code, r.started_at, r.finished_at, r.retry_of_run_id
FROM public.heartbeat_runs r
WHERE r.company_id = $1 AND r.agent_id = $2
  AND (r.context_snapshot->>'issueId' = $3 OR r.retry_of_run_id = $4::uuid)
  AND r.created_at > now() - interval '7 days'
ORDER BY r.created_at DESC LIMIT 5;
```

**Other query rules:**

- **WIP:** a planned owner's non-ops items that are assigned **to that planned owner**, in `todo` or `in_progress`. Board-policy hand-backs to the PM do not count, and `in_review` and `blocked` free the slot.
- **"Done since last release, not in a version":** the project's tasks done after the last `released_at` that have no item row and are not routine executions, plugin operations or anchors.
- **Missed runs:** read from `heartbeat_runs` through `context_snapshot->>'issueId'`, which is indexed (packages/db/src/schema/heartbeat_runs.ts:150-152).
- **Missed documents:** found through `issue_documents (company_id, key, updated_at)`, which every update touches (documents.ts:394-397), and then fetched with `ctx.issues.documents.get`.
- **Comments:** comment author and run come from `issue_comments` (`author_user_id`, `author_agent_id`, `created_by_run_id`).
- **Writes** use compare-and-set: `ctx.db.execute('UPDATE … SET …, row_version = row_version + 1 WHERE id=$1 AND company_id=$2 AND row_version=$3')`. A rowCount of 0 answers 409.

### 7.4 Background work: timer, job, events

- **Enabled companies** come from a map that `onConfigChanged` fills. The host replays every stored config at worker start (plugin-loader.ts:2370-2410) and on each save.
  - Every 10 minutes the plugin re-reads `ctx.config.get(companyId)` in try/catch and drops companies whose config is gone.
  - The worker **never** calls `ctx.companies.list()` outside an invocation. That call is treated as a wildcard and fails whenever any host invocation is live (plugin-worker-manager.ts:2652, 2686-2688; host-client-factory.ts:621-628). Event notifications keep invocations live for 15 minutes (:3466-3471).
- **Timer and drain loop.** `setup()` starts both, outside any invocation context:
  - the **drain loop** debounces dirty companies for 2 s;
  - the **timer** runs every 60 s.

  Their calls name the configured company, so they get its proactive scope (:2667-2693), or name no company at all (`ctx.db.query`). Both run one company at a time under the mutex.
- **Job.** The manifest job `roadmap-tick` runs on `*/15 * * * *`. It is the visible backstop: a full pass, pruning and config re-validation. A per-minute job would add about 1,440 `plugin_job_runs` rows a day, and nothing deletes those rows (plugin-job-scheduler.ts:352-395).
- **Events,** subscribed unfiltered in `setup()`:
  - issues: `issue.created`, `issue.updated`, `issue.comment.created`, `issue.document.created`, `issue.document.updated`, `issue.relations.updated`;
  - runs: `agent.run.finished`, `agent.run.failed`, `agent.run.cancelled`;
  - agents: `agent.updated`, `agent.error_cleared`;
  - approvals and budgets: `approval.created`, `approval.decided`, `budget.incident.resolved`;
  - `company.updated`, `project.updated`.

  The plugin does not subscribe to `agent.status_changed`, because nothing emits it (constants.ts:1707 is its only occurrence). Owner availability is otherwise timer-driven, within 60 s.

  The handler ignores the plugin's own events (actorType `plugin`, actorId = this plugin) and companies that are not enabled. Otherwise it only marks the company dirty with the touched ids.

### 7.5 Reconcile(company), under the mutex

Each step is isolated: a failure is logged, flagged once in Needs-you, and the next step still runs.

1. Agent documents (`doc_inbox`): `version-plan`, `roadmap-fixes`, `release-record`, `qa-report`.
2. Anchor turns:
   - turn-end checks (§3.3);
   - turn requests from human comments, where `issue_comments.author_user_id` has a board role and `created_by_run_id` is null;
   - anchor drift (§3.2).
3. Card outcomes: `listInteractions` on anchors that have a pending card.
4. Adoption: marker tasks (only on `issue.created`, creator-checked) and top-level `type:bug` tasks (P2).
5. Item drift. Three cases:
   - items of a draft or planned version that are not parked (except items carried in flight and done or cancelled items);
   - items of any version that are unassigned in `todo` or `blocked`, which is core release: re-park in one write, so orphan recovery cannot take them, then hand out again;
   - parked items that have a live run.
6. Dependencies: items blocked by tasks outside started work, and dependents of moved items.
7. Completion edges and notices.
8. Patch thresholds (P2).
9. Late scope, revision requests, cancelled release tasks, release detection and confirmation (P2).
10. Closing `group` items whose children are all terminal (0 wakes).
11. Triage tasks when fixes wait (P2).
12. Stall checks, which feed Needs-you and the `stalled` notices (§10).
13. Hand-out pass (§7.6).
14. Delivery of notices and cards, including re-posting an expired card whose precondition still holds (at most once per 6 h per kind).

### 7.6 Hand-out engine

- **Order:**
  1. anchor turns and ops items (release steps, triage);
  2. critical fixes and backports;
  3. other stream and releasing-version bug items, by priority;
  4. feature items, by the version's `started_at`, then rank, then `created_at`.
- **Readiness.** All of these must hold:
  - the task is still parked, or, for an explicit request, still in the expected state;
  - the version state allows it (the query above);
  - blockers are done or cancelled, hidden ones included, mirroring `requestWakeup` (plugin-host-services.ts:2175-2181);
  - the owner is not paused, in error, terminated or pending approval (constants.ts:16-24);
  - there is no invocation block: the company is not paused, the project is not budget-paused, and no open hard incident exists for the company, the project or the owner (the mirror query, matching budgets.ts:745-860);
  - the item is not backed off;
  - the WIP slot is free. Ops items, critical fixes, backports and Hand out now are exempt.
- **Write.**
  1. One update `{assigneeAgentId, assigneeUserId: null, status: 'todo', executionPolicy}`. S5 computes rev5 §11.2's `expectedPolicy` from `review_route` for items with `review` set; without S5 the update carries no policy.
  2. One `requestWakeup` with key `roadmap:handout:<issueId>:<n>`. The engine never uses `requestWakeups`, which aborts at the first refusal.
  3. `handed_out_at` and `handout_count` are set and an `events` row is written. This also serves the explicit request.
- **Pending requests are cleared** (`handout_requested_at = NULL`) by Reopen, Re-park, any move and Cancel, so a re-parked task is never handed out again by a stale request. A test covers an anchor that returns to the board after a turn: the next pass makes 0 hand-outs.
- **Created tasks** never carry `actorAgentId`. Orphan recovery picks only tasks with an agent creator (recovery/service.ts:2215-2240).
- **Refusal** (the wake throws):
  - work items are re-parked in one write, backed off for 15 minutes (doubling up to 2 h) and flagged;
  - ops items return to their previous holder (the anchor goes back unassigned with its state status; release and triage tasks are re-parked). A `stalled` notice follows after 30 minutes.
  - Events (`agent.updated`, `agent.error_cleared`, `budget.incident.resolved`, `company.updated`, `project.updated`) clear backoffs for the affected scope.
- **Budget:** `handoutsPerMinute` (≤ 3) per rolling 60 s, counted by the bucket query.

## 9. PM, engineer and DevOps instructions

### 9.1 Where instructions live

The plugin generates the instructions into task descriptions, so they are always in the agent's run context and always current:

- the anchor brief;
- the triage brief;
- the footer of every generated work, fix or backport task;
- the release checklist.

Nothing has to be installed, attached or reset. The bundled `paperclip` skill, its Board policy (skills/paperclip/SKILL.md:14-23) and each agent's AGENTS.md stay unchanged. Every instruction uses only bridge-allowed core routes.

### 9.2 Planning brief: the description of `Roadmap: Acme iOS 1.3` (P3)

```
Roadmap-Version: <versionId> · Acme iOS 1.3 · thread of <Roadmap owner>
You are this project's PM. This task is the planning thread for Acme iOS 1.3. Planning only: write no code.
Goal: <board text>   Target: <date|none>

Each turn:
1. Read the newest comments first. The board answers you here; its reply brings this task back to you.
2. Keep the document `version-plan` on this task current (not `plan`): short prose (scope, order, risks), then exactly
   ONE fenced json block with schema paperclip.roadmap/version-plan@1 (status draft|ready; tasks[] with key, title,
   description, acceptance, kind feature|bug|chore|group, owner from the agent list, rank, priority, dependsOn,
   parent, epic, review; existing[] with issue, include|leave, owner, rank; questions[]).
   One task per deliverable that one agent can finish and hand back.
3. After each save, read the document `plan-check` on this task. It names the revision it checked; if it names an
   older one, wait about 10 seconds and read again (at most 3 times). Fix every error and save again.
4. Ask open questions in one comment. Keep status draft until the board has answered; set ready when complete.
   Then end your run. Do not change this task's status or assignee: the Roadmap hands it over.
Never: create, assign or start tasks; post request_confirmation, suggest_tasks or approvals on this task; create labels;
touch unassigned backlog tasks. After the board approves, the Roadmap creates every task parked; nothing starts before
the board presses Start. If a directive says 'Implement the accepted plan', it does not apply to this task: end the
run with one comment.
Agents: MobileEngineer (engineer, active) · QAEngineer (qa, error) · …   Open tasks you may include: ACM-41 (todo) · …
Plan: rev 4 (draft) · last board decision: request changes, 'split the payments task'
```

### 9.3 Reply turns (P3)

Once the plan is approved, the anchor description switches to the version-thread text. It keeps the first line and adds:

```
When this task is assigned to you, the board has written to you here. Answer its newest comment in one comment and end
the run. Scope changes go through the board's Revise plan: edit `version-plan` only when plan-check says a revision is
open. Do not change this task's status or assignee.
```

**Before P3,** the thread text says: "Comments here do not reach the PM yet; talk to the PM on its own task."

### 9.4 Interim planning convention (P1-P2, until the materializer)

1. The board creates a core task `Plan Acme iOS 1.3`, assigned to the PM, with the version's marker line.
2. The PM plans there and writes `version-plan` (same schema).
3. The PM asks for approval with one `request_board_approval` linked to that task and sets it `in_review`. A pending linked approval is a valid review path (routes/issues.ts:2008-2019).
4. Approving wakes the PM (routes/approvals.ts:359-385). That wake injects no accepted-plan directive.
5. The PM creates the tasks as status `backlog` with no assignee, a first line `Roadmap-Version: <id>`, and `Planned-Owner: <agent>` / `Rank: <n>` lines.
6. The plugin adopts each task (§7.2, creator-checked) and flags any task that is not parked.

**Board guidance:** for this approval, reject with a reason rather than Request revision, which wakes nobody.

### 9.8 Release agent and QA

- **Release agent.** Follows the checklist (§5.5).
  - It waits in `in_review` only on its own linked go/no-go.
  - It never pushes a branch, moves a tag, deploys before a required approval, or creates tasks.
  - When something fails, it hands back to the PM (todo + PM) with the error.
- **QA (P4 chain).** Verifies the candidate sha named by its task and writes `qa-report`.
  - On PASS: marks the task done.
  - On FAIL: puts the bugs under Proposals and hands the task back to the PM.

### 9.9 How "Implement the accepted plan" is overridden

That directive is injected only when an accepted plan confirmation wakes the agent assignee (heartbeat.ts:8928-8931). The design takes four measures against it:

1. **Structurally.**
   - The plan document is `version-plan`, and core's plan-confirmation path matches only the key `plan` (routes/issues.ts:851-854). An accepted Approve-plan card therefore never sets up the accepted-plan continuation or its automatic converting-plans skill.
   - The card also sits on an unassigned anchor, and continuation returns at once without an agent assignee (routes/issues.ts:2564-2565).
   - In the interim convention, the decision is a `request_board_approval`, whose wake carries no plan directive.
2. **Defensively.**
   - `plan.approve` refuses while the anchor has a live PM run.
   - The plugin creates the tasks itself, so a PM that follows the directive has nothing to create.
   - Marker adoption is creator-checked, and drift detection flags tasks that are not parked.
   - Any pending card on an anchor that a PM created is shown as "not the Roadmap's plan approval" in Needs-you.
3. **Textually.** The brief forbids cards, `plan` documents and decompositions, and says the directive does not apply. The converting-plans line "independent work can start now" (skills/paperclip-converting-plans-to-tasks/SKILL.md:18-20) never loads.
4. **Residual risk.** Suppose a PM writes a `plan` document and its own card out of habit, and a board member accepts that card while the PM holds the anchor. One continuation wake can then queue with the directive. The textual override and drift detection cover this case.

### 9.10 Board-policy fit (skills/paperclip/SKILL.md:14-23)

| Policy rule | How the design follows it |
|---|---|
| Only the coordinator creates and assigns | The plugin is not an agent, and it acts only on board decisions or on the PM's documents:<br>- it creates tasks from an approved plan, a Cut, a board Report bug, or the PM's `roadmap-fixes`, plus PM coordination tasks (triage);<br>- it assigns parked tasks to the planned owners of a board-approved plan after Start, to owners the PM chose, or to an ops task's planned owner;<br>- it never reassigns a task that is in flight;<br>- marker tasks from other agents are never handed out. |
| Children only inside an approved scope | Version tasks come from the approved plan revision. Stream fixes sit under the stream anchor's standing scope, which the board approved when it enabled the project. |
| Follow-ups are Proposals | Bugs stay Proposals until the PM files them. Agent-created `type:bug` tasks are only surfaced for triage. |
| Hand-off = todo + assign the coordinator; mentions are context only | Unchanged. Notices use `user://` mentions only to bring an archived anchor back (heartbeat.ts:27904-27906). |
| `in_review` needs a real review path | Only the release agent's own linked approval or an execution-policy stage. The plugin never leaves an anchor in `in_review`. |
| Light runs | One planning turn, reply, triage batch or release per run. There is no daily routine: triage tasks appear only when fixes wait. |

### 9.11 Board guidance (shown in the Roadmap help)

- Talk to the PM about a version by commenting on its thread (from P3). Each comment costs one PM run.
- Change scope after approval with **Revise plan**.
- For a go/no-go, reject with a reason or use Request revision; the Roadmap passes both back to the release agent.
- Do not lock the `version-plan` document: the approval already pins the exact revision.
- Do not assign or close a thread task. If it happens, press **Restore**.
- In week 1, measure PM runs in Costs (cost_events) and set each PM's `maxDailyRuns` above the observed peak. Task wakes over the cap are deferred to the next day, not dropped (heartbeat.ts:17388-17405).

## 10. Notifications

### 10.1 How a notice reaches the board

1. **The anchor carries the notices.** Every notice is a plugin comment with no author on the version's anchor, or on the stream anchor. The anchor was created in the Roadmap owner's name and is never assigned to a user.
2. **Unread for the owner.** For a creator, the last touch is `createdAt` plus the creator's own reads and comments. A comment with a NULL author created after that counts as unread, which raises the Inbox badge (services/issues.ts:2847-2876, 2926-2936, 2985-3004; ui/src/lib/inbox.ts:1297-1313).
3. **Why the anchor is never assigned to a user.** An assignee's last touch is `issues.updatedAt`, and `addComment` bumps `updatedAt` right after it inserts the comment (services/issues.ts:12566, 12779-12783). A comment on a task assigned to the owner would therefore never be unread for them (server/src/__tests__/issues-user-context.test.ts:65-77).
4. **Archived anchors come back.** Every notice mentions the owner as `[@Name](user://<id>)` (services/issues.ts:3044-3060).
5. **Plugin comments never wake an agent.** Only human-attributed comments wake anyone (plugin-host-services.ts:2430-2442), and the plugin does not request that capability.
6. **Notices are rows.** Each is posted once per edge and generation, with up to 10 attempts. After that, Needs-you reports the failure.
7. **Cards accompany the notices.** A decision card goes with its notice: a `request_confirmation` with `human_only`, continuation `none`, on the unassigned anchor.
   - A card alone does not mark a task unread; it only brings an archived item back (services/issues.ts:3006-3027). That is why every card has its comment.
   - Accepting a card wakes nobody (routes/issues.ts:2564-2565).
   - The timer polls `listInteractions` within 60 s, re-checks the preconditions and the resolver, acts as that user, and marks the card `acted`.
   - Only the plan card sets `supersedeOnUserComment`, because core expires every pending supersedable card on any human comment (issue-thread-interactions.ts:4316-4356).
   - The plugin cannot withdraw a card. A stale card that gets accepted is answered and marked `stale`. Core expires the anchor's cards when the anchor closes (services/issues.ts:11149-11163).

### 10.3 Who sees what

- **Unread status** reaches the anchor's creator (the Roadmap owner) and any board member who has commented on or changed the anchor (services/issues.ts:2847-2876). A mention alone does not make a member a participant.
- **Every board member** sees native go/no-go approvals, the dashboard widget, Needs-you and the sidebar pill.
- **Off the app** (P4, optional): one POST per notice to a Telegram or Discord incoming webhook, through `http.outbound`, with the secret ref in the company's config row. Core has no push channel and no chat client for plugins.

### 10.4 Never used

- mention wakes, which core drops (heartbeat.ts:27904-27906);
- plugin-created approvals, which do not exist (sdk protocol.ts:2113-2121);
- status-only writes, which do not bring archived items back because the host stores the status under `details.patch` (plugin-host-services.ts:1971-1985);
- experimental Decisions, Status Cards or Pipelines.

### Diverges, and why

3. **The plugin creates the approved plan's tasks.** It is deterministic, costs 0 wakes, and never triggers the accepted-plan continuation.
4. **A standing fix stream** instead of one patch per hotfix that auto-stabilizes, which cannot meet U8. Version order is checked per release line.
5. **Notices reach the core Inbox** through creator-only, unassigned anchors, cards and native approvals, instead of plugin-only Needs-you items (rev5's U6 gap). A board-assigned anchor would never show unread (§10.1).
6. **`releasing` replaces `stabilizing`.** Scope freezes at the Cut and unfinished work moves out Jira-style; there is no merge window.
7. **Agents talk to the plugin only through documents** on tasks they hold. There are no tools or plugin REST calls, because the sandbox bridge has no `/api/plugins` route. The plan key is `version-plan`, so core's `plan` machinery stays out of the way.
8. **Instructions live in generated task descriptions,** not in a shared skill.
9. **The only foreign key is to `public.companies`.**
10. **Enabling a company is a `plugin_config` row,** because background work needs its proactive scope. Rev5 used `company_settings` and missed this.
11. **Plugin-created tasks are children of their anchor.** This gives agents' runs a responsible user and shows the version in their context. Rev5 left creates top-level.
